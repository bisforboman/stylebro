# Proposal: SA1108 (comments between a statement's header and its block)

Status: prototype on branch `proposal/sa1108` as **BRO1132**. The rule's behavior (what the fix does) needs the
owner's decision before it lands.

## What StyleCop does

Source: `SA1108BlockStatementsMustNotContainEmbeddedComments.cs` (StyleCopAnalyzers master) and `documentation/SA1108.md`.

- **Blocks checked:** a `Block` whose parent is `if`, `else`, `for`, `foreach`, `while`, `do`, `lock`, `try`, `catch`,
  `finally`, `checked`, `unchecked` or `fixed`, plus the braces of a `switch` statement. Not checked: `using`, a
  deconstructing `foreach (var (a, b) in ...)` (a different syntax kind), method/local function/lambda bodies, plain
  blocks.
- **Comments checked:** only the trivia between the token before `{` and `{` itself: the trailing trivia of that token
  (`if (x) // c`) and the leading trivia of `{` (a comment on its own line, or `/* c */ {`). A comment inside the
  condition, after `{`, or above the statement is fine.
- **Comment kinds:** `//` and `/* */`. `////` (commented-out code) is exempt. `///` is exempt when documentation
  comments are parsed (it is then documentation trivia, not a comment).
- One diagnostic per comment, on the comment. **No code fix.** The docs say to move the comment above the statement,
  into the body, or remove it.

## Probe (StyleCop 1.2.0-beta.556)

Parity set `scripts/stylecop-survey/parity/embedded-comments/Comments.cs`, run by `Compare-WithStyleCop.ps1`. StyleCop
reported exactly what the source says, 22 positions:

| Reported | Not reported |
|---|---|
| `if (x) // c`, `else if (x) // c`, `else // c` | `////if (!a)` between `)` and `{` |
| `// c` on its own line between `)` and `{` | `{ // c` (after the brace) |
| `while (x) /* c */ {` (K&R) | `if (/* c */ a)` |
| `foreach`, `for`, `do`, `lock`, `try`, `catch (E) when (...)`, bare `catch`, `finally`, `checked`, `unchecked`, `switch` | `/// c` (docs parsed) |
| two comments in one gap (`/* a */ // b`): two diagnostics | `using (...) // c`, `foreach (var (x, y) in ...) // c` |
| empty block, block that already starts with a comment | plain block, lambda, method and local function bodies, `if (a) // c` without braces |

StyleBro reports the same 20 positions; the 2 it doesn't are the documented skips below.

|---|---|---|
| FFMpegCore | 6 | no StyleCop |

| Serilog | 4 | no StyleCop |
| Jellyfin | 19 | StyleCop, but **SA1108 turned off** in `.editorconfig` |
| Polly | 0 | SA1108 warning |
| OpenTelemetry | 0 | SA1108 warning |

All 34 are `//` comments trailing the header on its line (`if (...) // c`, `else // c`, `catch (...) // c`,
`while (...) // c`). None is on its own line, none is `/* */`, none is in a `switch`. Kinds: 23 `if`/`else if`, 6 `else`,
3 `catch`, 2 `while`.

Representative examples:

```csharp
// FFMpegCore, FFMpegCache.cs (6 of these: double-checked locking)
if (_pixelFormats == null) //First check not thread safe
{
    lock (_syncObject)
    {
        if (_pixelFormats == null) //Second check thread safe
        {

// Newtonsoft.Json, EnumUtils.cs / LinqBridge.cs / EnumUtils.cs
else // These are flags OR'ed together (We treat everything as unsigned types)

```

The hard case, 4 of 34: a multi-line condition where the comment annotates the **last operand**, often one of a
column of per-operand comments:

```csharp

    && Uri.TryCreate(stream.Path, UriKind.Absolute, out Uri? uriResult) // Path must be an absolute URI
    && (uriResult.Scheme == Uri.UriSchemeHttp || uriResult.Scheme == Uri.UriSchemeHttps)) // Scheme must be HTTP or HTTPS

    // All conditions met, override with the direct path
```

Same shape in Jellyfin's `EncodingHelper.cs` (`// av1 (av1_qsv)`), `ProbeResultNormalizer.cs` and Newtonsoft.Json's
`DateTimeParser.cs` (`// hour can be 24 if minute/second is zero)`).

## Options

**(A) Into the block, on its own line right after `{`** (prototyped). Every comment of the gap, in order, indented like
the block's first line, above any comment already there.

```csharp
// Before                                   // After
if (version < MinVersion) // Below minimum  if (version < MinVersion)
{                                           {
    Warn();                                     // Below minimum
}                                               Warn();
else // Used in testing only.               }
{                                           else
    Init();                                 {
}                                               // Used in testing only.
                                                Init();
                                            }
```

- Pro: works the same for every statement and clause (`else`, `catch`, `finally`, `else if`), one of the two places
  StyleCop's docs name, and what SA1108-clean code (Polly, OpenTelemetry) looks like. In 30 of the 34 real cases the
  comment describes the branch, and reads naturally there.
- Pro: no interaction with blank-line rules: BRO1504 doesn't want a blank line directly after `{`, BRO1503 is about
  blank lines, not comments.
- Con: an operand annotation (the hard case) ends up above the body, where it reads as a note about the body, and in
  StreamInfo above another comment:
  ```csharp
  {
      // Scheme must be HTTP or HTTPS
      // All conditions met, override with the direct path
  ```

**(B) On its own line above the statement.**

```csharp
// Below minimum
if (version < MinVersion)
{
```

- Pro: reads well for a comment about the whole condition (`// Version is below what we recommend`).
- Con: there is no "above" for `else`, `catch`, `finally` and `else if` (13 of the 34): above them is the previous
  block's `}`. Putting the comment between `}` and `else` compiles but looks broken, so these need (A) as a fallback:
  two behaviors for one rule.
- Con: moves the comment away from the operand it may annotate, even further than (A).
- Con: must also add BRO1504's blank line above the comment when code precedes it (else a second `dotnet format` run),
  and respect `#if`/labels above the statement.

**(C) To the end of the `{` line** (`{ // c`).

```csharp
if (version < MinVersion)
{ // Below minimum
    Warn();
}
```

- Pro: smallest move; the comment stays next to the condition. Not SA1108 (StyleCop doesn't check trivia after `{`),
  and SA1500 doesn't count a comment as code sharing the brace's line.
- Con: `{ // c` is an unusual layout that most style guides (and people) would call odd; it's arguably what SA1108
  exists to discourage. For K&R code (`while (x) /* c */ {`) it becomes `while (x) { /* c */`.

**(D) Report only, no fix.** Not allowed by StyleBro's design (every rule has a fix `dotnet format` applies): the rule
would stay dropped, as it is on `main` today.

**(A') = (A), but skip multi-line headers.** Not reported when the statement's header spans several lines, which are
exactly the 4 operand-annotation cases found. Loses parity with StyleCop on those (documented deviation), keeps every
moved comment meaningful.

## Recommendation

**(A)**, possibly as **(A')**. (A) is the only option with one behavior for every statement and clause, matches one of
StyleCop's two suggested places, and gives natural results for the large majority of real cases. Whether to skip
multi-line headers (A') is the open question: it trades 4 of 34 StyleCop positions for never producing a misleading
comment. I'd lean to (A') if the owner values "the fix never makes code worse" over exact parity.

Second question: the preset. StyleCop has SA1108 on by default and Polly/OpenTelemetry enforce it, but Jellyfin turned it
off. The prototype puts BRO1132 in the preset at warning, like StyleCop; `stylebro-migrate` carries a repo's off setting
over (SA1108 off -> BRO1132 off).

## What the prototype implements

Option (A), on branch `proposal/sa1108` (not merged, no PR):

- `src/StyleBro.Analyzers/Readability/EmbeddedComments.cs` (shared logic), `EmbeddedCommentAnalyzer.cs` (a tree action:
  the comment after the header lies outside the block's span), `src/StyleBro.CodeFixes/Readability/EmbeddedCommentCodeFixProvider.cs`.
- Which blocks and comments: StyleCop's, exactly. The fix removes each comment where it is (a line left blank goes
  completely, using BRO1101's per-line edit logic) and inserts the comments after `{`, indented like the block's first
  line (one indentation unit deeper than `{` in an empty block). All comments of one gap are fixed together, so a single
  fix and Fix All agree.
- Skipped (no diagnostic): a single-line block (`{ y(); }` on the `{` line: no line to put the comment on), a comment
  spanning lines, a directive between the header and `{`.
- Hand-off: BRO1504 (blank line before a `//` comment that follows code) no longer reports a comment on its own line
  between `)` and `{` while BRO1132 is on. Without that, the Messy sample showed an order dependence: BRO1504 added a
  blank line above the comment, BRO1132 then moved the comment, and the blank line stayed before `{` (BRO1501 on the
  next run).
- Docs and listings: `docs/rules/BRO1132.md`, README row, differences page (reports less: the skips; different fix:
  StyleCop has none), `AnalyzerReleases.Unshipped.md`, preset (warning), `decisions.psd1` (moved from `skipped.psd1`),
  regenerated mapping/skipped/backlog docs, Messy sample `Notes.cs`, mutation entries for every guard (all killed).
