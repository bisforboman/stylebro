# Types with a generated part keep the order of their fields and properties (2026-10-16)

## Question

Trial 26: BRO1001 sorted the members of a `[GenerateSerde] partial class Point { public int x { get; set; } public
int y_value; }`, and the JSON the Serde source generator writes changed from `{"x":1,"yValue":2}` to
`{"yValue":2,"x":1}`: the generator writes the members in declaration order. BRO1001 keeps that order only for types
with a serializer attribute it recognizes by name (`Json`, `DataContract`, `MessagePack`, ...). Should a partial type
that a source generator extends keep the order of its fields and properties too?

## Choices

1. **Skip types with a generated part**: a partial type with a part in generated code (the signal the rename guards
   use: a `.g.cs`/`.designer.cs` file name or an `<auto-generated>` header) keeps the relative order of its fields and
   properties: when sorting would change that order, the type isn't sorted at all (like a serialized type); a sort that
   keeps it still applies.
2. Add Serde's attribute to the serializer names: covers this generator only.
3. Leave it: the user restores the order by hand.

## Decision

**Choice 1** (owner's choice 2026-10-16: "Skip types with a generated part"). It also covers WPF/WinForms/Razor
code-behind classes (their markup compiler writes a part): their fields and properties keep their order. Correction
(trial 27): a type whose sort would reorder them is skipped as a whole, so its methods aren't sorted either; one whose
fields and properties are already in sorted order is still sorted.
