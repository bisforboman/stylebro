# BRO1405: Statement should not use unnecessary parenthesis

Parentheses around a single value, or around a whole expression where nothing binds to it, are removed. Replaces
StyleCop **SA1119**.

## Example

### Before

```csharp
public class Totals
{
    private int count = (1 + 2);

    public int Sum(int a, int b)
    {
        var total = (a + b);
        return (total);
    }
}
```

### After

```csharp
public class Totals
{
    private int count = 1 + 2;

    public int Sum(int a, int b)
    {
        var total = a + b;
        return total;
    }
}
```

## Why

Parentheses that don't group anything make the reader look for a precedence question that isn't there.

## How the fix works

The fix removes `(` and `)` and any spaces just inside them; where the tokens would run together (`return(x)`), a
space is left. Before removing, the statement (or member) is parsed again without the parentheses, and they're only
removed when the result means the same: parentheses can turn `F(a < b, (c > (d + 1)))` into a generic method call
`a<b, c>(d + 1)` when they go.

Like StyleCop, parentheses inside an operator expression (`a + (b * c)`, `a ?? (b ?? c)`) are left alone: they say how
the expression groups, or make it clearer. Adding parentheses for clarity is SA1407/SA1408 (the SDK's IDE0048).

This rule replaces the SDK's IDE0047, whose fix writes merge conflict markers in multi-targeted projects under
`dotnet format` and which also removes `a ?? (b ?? c)` (see [decisions](https://github.com/bisforboman/stylebro/blob/main/docs/decisions.md)).

## Not reported

StyleCop's exceptions: operator expressions inside other expressions, a conditional in an interpolation
(`$"{(f ? 1 : 2)}"`), a conditional access before `.`/`[]` (`(s?.Length).ToString()`), a `switch` or `with`
expression that is called, cast or accessed, `stackalloc` in an initializer, the left side of a `ref` conditional
assignment. Also: parentheses with a comment inside them, and ones whose removal would change how the code parses.

## Configuration

The SDK's `dotnet_style_parentheses_*` settings don't change this rule: it removes what StyleCop's SA1119 removes. With
`never_if_unnecessary` the SDK would also remove parentheses inside operator expressions (`a ?? (b ?? c)`); StyleBro
leaves those, so a StyleCop-clean codebase stays unchanged after migrating. `never_if_unnecessary` does turn off adding
parentheses ([BRO1406](BRO1406.md), [BRO1407](BRO1407.md)).

## Compared with StyleCop

Same positions, except the parse-changing case above, where StyleCop's fix doesn't compile. StyleCop's fix leaves the
spaces of `( b )` behind.

StyleCop also reports a hidden SA1119_p on the same parentheses' `(` and `)`, only so the IDE greys them out; StyleBro
doesn't grey them (the warning is the same). Neither checks parentheses in patterns (`x is (> 0)`).
