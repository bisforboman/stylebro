# BRO1001: Members should be ordered

Members of a class, struct, record or interface, and the types and namespaces of a namespace or file, should appear in
a fixed order: by kind, then accessibility, then constant/static/readonly. Replaces StyleCop **SA1201, SA1202, SA1203,
SA1204 and SA1214**.

## Example

### Before

```csharp
using System.Collections.Generic;

public class Order
{
    public void Ship()
    {
    }

    private readonly List<string> _lines = new();

    public Order(string id)
    {
        Id = id;
    }

    public string Id { get; }
}
```

### After

```csharp
using System.Collections.Generic;

public class Order
{
    private readonly List<string> _lines = new();

    public Order(string id)
    {
        Id = id;
    }

    public string Id { get; }

    public void Ship()
    {
    }
}
```

## Why

When every type follows the same order, you know where to look: state first, then construction, then the API. It
also keeps reviews focused, because nobody argues about where a new member goes.

## The order

Members are sorted by these keys, in this order:

1. **Kind**: field, constructor, finalizer, delegate, event, enum, interface, property, indexer, conversion, operator,
   method, struct, class
2. **Accessibility**: public, internal, protected internal, protected, private protected, private. A static
   constructor counts as public, like in StyleCop.
3. **Constants** before other fields
4. **Static** before instance
5. **Readonly** fields before mutable fields

Members with equal keys keep their existing relative order. These are StyleCop's defaults.

In a namespace (block or file-scoped) or at the top of a file, the same keys order its namespaces and types: namespaces
first, then delegates, enums, interfaces, structs and classes (records count as classes or structs). A type without an
access modifier is internal there, and a part of a partial type without one counts as what its other parts declare
(so the order doesn't change once [BRO1007](BRO1007.md) adds the modifier).

## Configuration

```ini
[*.cs]
stylebro_member_order = field, constructor, property, method
stylebro_member_access_order = public, internal, protected, private
stylebro_member_constants_first = true
stylebro_member_static_first = true
stylebro_member_readonly_first = true
```

Kinds and accessibilities you leave out keep their default relative order, after the ones you list. `conversion` means
conversion operators (`implicit operator`/`explicit operator`); `operator` means all other operators.

## How the fix works

The fix sorts the whole type, reported once per type on the first member that is out of place. The blank-line layout
stays in place, while comments, XML docs and attributes move with their member. A member with a `//` comment above it
that lands directly below another member gets a blank line above the comment, so the sort doesn't leave a comment
glued to the code above it ([BRO1504](BRO1504.md)). Nested types are sorted too, so one
`dotnet format analyzers --diagnostics BRO1001` run is enough.

If the project uses `TreatWarningsAsErrors`, don't exempt the rule with `<WarningsNotAsErrors>BRO1001</WarningsNotAsErrors>`:
`dotnet format` then skips BRO1001 entirely and fixes nothing, although the build still reports it. Set the severity in
`.editorconfig` instead (`dotnet_diagnostic.BRO1001.severity = suggestion`), or run `dotnet format` before building.

## Regions

Members are sorted within each region: every `#region` or `#endregion` line between members is a fence, and the
members between two fences are sorted on their own. The region lines, and comments above them, stay where they are, so
every region keeps its members. `#pragma` and `#nullable` lines are fences too, so every member keeps the warnings and
nullable context it had. The order across regions isn't checked (StyleCop's is): fixing it would mean moving
members into another region. A doc comment that moves right below a region line gets a blank line above it
([BRO1513](BRO1513.md)).

## Not reported

- **Types with `#if`, `#elif`, `#else` or `#endif` between members**, and namespaces or files with them between types.
  In a multi-targeted project each target framework sees other members there, and the copies of the file would need
  different edits. Also a doc comment above a directive, which would stay with the position instead of its member.
- **Members out of order across regions** (see Regions).
- **Types whose member order the runtime sees**, when sorting would change it: instance fields of a struct (sequential
  layout is the default) or of a type with `[StructLayout]` (memory layout for interop, `unsafe` code and `Marshal`), and
  fields and properties of a type with a serializer attribute on it or on a member (Json.NET, DataContract,
  XmlSerializer, MessagePack, protobuf write members in declaration order). Found on Newtonsoft.Json, whose tests
  compare JSON text. Other members of such a type are still sorted when that keeps the order of these. A class that is
  serialized without any attribute can't be recognized and is sorted (StyleCop's fix reorders those too).
- **Files whose first type carries the file header**: with no `using` or namespace before it, the header comment
  belongs to the first type and would move with it.
- **Files with top-level statements.**
- **Types where sorting would change what field initializers compute.** Initializers run in source order, so moving
  `B` above `A` here (readonly first) would make `B` 1 instead of 6:

  ```csharp
  public static class C
  {
      public static int A = 5;
      public static readonly int B = A + 1;
  }
  ```

  A type is skipped when sorting would swap two static initializers, or two instance initializers, and either of them
  mentions a member of the type (directly or through a method), or creates an instance of the type (`new()` in a
  singleton). `typeof`, `nameof` and names on other objects (`text.Length`) don't count. Side effects outside the type,
  such as two initializers calling the same external counter, aren't detected.

## Compared with StyleCop

StyleCop reports every misplaced member; BRO1001 reports each type (or namespace, or file) once and fixes all of it. StyleCop doesn't
skip types where sorting changes initializer results. The member order itself is the same, checked pairwise for all
14 member kinds against StyleCop 1.1.118.
