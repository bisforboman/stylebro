# BRO1110: Closing parenthesis or bracket should be on the line of the last item

A parameter or argument list ends on the line where its last item ends, not with the closing parenthesis on a line
of its own. Replaces StyleCop **SA1111**.

## Example

### Before

```csharp
public class Mailer
{
    public void Send(
        string to,
        string subject
        )
    {
        Log(
            to,
            subject
            );
    }

    private void Log(string to, string subject)
    {
    }
}
```

### After

```csharp
public class Mailer
{
    public void Send(
        string to,
        string subject)
    {
        Log(
            to,
            subject);
    }

    private void Log(string to, string subject)
    {
    }
}
```

## Why

A lone `)` is a line that says nothing, and it makes the end of a call look like the start of a block. It's also
the C# convention in the .NET runtime and most libraries.

## How the fix works

The `)` or `]` moves right after the last item. A comment at the end of the last item's line goes after it:
`string subject // required` then `)` becomes `string subject) // required`.

Checked: the same lists as [BRO1109](BRO1109.md), plus lambda parameter lists.

## Configuration

```ini
[*.cs]
# last_item (default, like StyleCop): ')' ends the last item's line; own_line: a split list's ')' gets its own line
stylebro_closing_parenthesis_placement = last_item
```

`own_line` is the layout CSharpier and Prettier write. It applies to **split** lists: lists whose last item starts on
a line below the opening token (`(`, or the name's line when [BRO1109](BRO1109.md) moves the `(` up there). Their
`)` or `]` goes on a line of its own, indented like the line with the opening token. A list that isn't split (every
item starts on the `(` line, even when the last one spans lines, like a lambda) keeps its `)` at the end of the last
item, as with `last_item`; a lone `)` there is still moved up.

```csharp
// last_item
Log(
    to,
    subject);

// own_line
Log(
    to,
    subject
);
Log(() =>
{
    Send();
});
```

Only the gap before the `)` changes, so whatever follows it stays with it (`) =>`, `) : base(...)`, `).Trim()`,
`); // done`). Indentation of a `)` that already has its own line isn't checked. In `own_line` mode a split list is
also not reported when a comment sits between the last item and the `)`, or when the list contains a directive (each
target framework's copy of the file may have another last item).

## Not reported

- **Empty lists** (`Send(` then `)`): that's spacing, not the last item's line.
- **A comment on its own line or a directive before the closing parenthesis.**
- **A comment at the end of the last item's line when code follows the parenthesis on its line** (`2 // two` then
  `); var x = 1;`): the code would end up behind the comment.

## Compared with StyleCop

StyleCop has no `own_line` option. With the default, same results as StyleCop, with the same fixed output, except the last case above, which StyleCop reports, and two
kinds of lists StyleCop doesn't check (neither 1.1.118 nor 1.2): target-typed `new(...)` and constructor initializers
(`: this(...)`, `: base(...)`). StyleBro treats them like any other argument list.
