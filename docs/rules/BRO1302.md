# BRO1302: Parameter names should begin with a lower-case letter

Parameters are camelCase: `count`, not `Count` or `_count`. Replaces StyleCop **SA1313**.

## Example

### Before

```csharp
public abstract class Shape
{
    /// <summary>Scales the shape.</summary>
    /// <param name="Factor">How much to scale by.</param>
    public abstract void Scale(double Factor);
}

public class Circle : Shape
{
    public double Radius { get; private set; } = 1;

    public override void Scale(double Factor) => Radius *= Factor;

    public static Circle Create() => new Circle().Resized(Factor: 2);

    private Circle Resized(double Factor)
    {
        Scale(Factor);
        return this;
    }
}
```

### After

```csharp
public abstract class Shape
{
    /// <summary>Scales the shape.</summary>
    /// <param name="factor">How much to scale by.</param>
    public abstract void Scale(double factor);
}

public class Circle : Shape
{
    public double Radius { get; private set; } = 1;

    public override void Scale(double factor) => Radius *= factor;

    public static Circle Create() => new Circle().Resized(factor: 2);

    private Circle Resized(double factor)
    {
        Scale(factor);
        return this;
    }
}
```

## Why

C# names locals and parameters in camelCase and everything else in PascalCase, so the case tells you at a glance
whether a name belongs to the method. For parameters it's also part of the API: callers see the names in
IntelliSense and use them in named arguments.

## How the fix works

The parameter and every use of it are renamed, anywhere in the solution: the body, `nameof`, named arguments
(`Resized(Factor: 2)`) and the `<param>`/`<paramref>` docs. The new name is built like for
[BRO1301](BRO1301.md): `Count` becomes `count`, `_count` becomes `count`, `URL` becomes `url`.

A parameter of an abstract, virtual or interface member takes the parameters of its overrides and implementations
along when they have the same name, so they stay in sync. Those parameters aren't reported themselves (their name
comes from the base, like in StyleCop); one that has a different name is reported on its own.

Checked: parameters of methods, constructors (including primary constructors of classes and structs), indexers,
operators, delegates, local functions, lambdas and anonymous methods.

**Renaming a public parameter is a source-breaking change** for callers outside the solution that use it as a named
argument. Code inside the solution is updated.

## Not reported

- **Record parameters** (`record Person(string Name)`): they become properties, which are PascalCase.
- **Parameters that keep the name of the parameter they override or implement.**
- **Partial methods.** Both declarations have to be renamed together.
- The same unsafe cases as [BRO1301](BRO1301.md): the new name is already used in the member, two names would get
  the same new name, the parameter names an anonymous type member or tuple element by inference, the member contains
  `#if`, or the name has no camelCase form (`_`, `_1`, `Class`).

When an override can't be renamed safely (its member already uses the new name), the base and the other overrides
are renamed and that override keeps its name.

## Compared with StyleCop

Same results as StyleCop, except for the skipped cases above; StyleCop reports `_` and `__` parameters. StyleCop's fix
for SA1313 only lowers the first letter, can't fix names that start with `_`, leaves overrides and implementations
behind (they are then reported), and under `dotnet format` applies only some of the renames per run.
