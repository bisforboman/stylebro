# BRO1311: Tuple element names should use correct casing

Element names in tuple types are PascalCase: `(int Count, string Name)`, not `(int count, string name)`. Replaces
StyleCop **SA1316**.

## Example

### Before

```csharp
internal class Inventory
{
    public (int count, string name) Largest() => (count: 3, name: "bolts");

    public string Describe()
    {
        var item = Largest();
        return item.name + ": " + item.count;
    }
}
```

### After

```csharp
internal class Inventory
{
    public (int Count, string Name) Largest() => (Count: 3, Name: "bolts");

    public string Describe()
    {
        var item = Largest();
        return item.Name + ": " + item.Count;
    }
}
```

## Why

Tuple elements are public fields of the tuple, so they read like members: `item.Name`, as for a property. Consistent
casing also keeps a tuple-returning method and a record or class returning the same data interchangeable.

## Configuration

```ini
[*.cs]
# PascalCase (default) or camelCase, like StyleCop's tupleElementNameCasing.
stylebro_tuple_element_name_casing = camelCase
```

`stylebro-migrate` writes it from `stylecop.json`.

`stylebro_rename_public_api = true` also renames names other assemblies see (default `false`, see Not reported; the owner's decision in [decisions.md](https://github.com/bisforboman/stylebro/blob/main/docs/decisions.md)).

## How the fix works

Tuple element names belong to the tuple type where they're written, and a use like `item.count` binds to the element
of whichever tuple type `item` has. So the fix renames the name everywhere at once, in the whole solution:

- every tuple type element with that name (a method's return type, a field, a local's type, a type argument);
- every name in a tuple literal converted to one of them (`(count: 3, ...)` returned from the method above), so the
  compiler doesn't warn that the literal's name is ignored (CS8123);
- every use of those elements: `item.count`, `item?.count`, `nameof(item.count)`, `item is (count: 1, _)`;
- overrides and implementations together with what they override: their names have to match (CS8139).

A tuple or anonymous object that takes its element name from a renamed use (`(item.count, 1)`, `new { item.count }`)
gets the old name written out (`(count: item.Count, 1)`), so it and its own uses keep working unchanged.
Deconstruction (`var (count, name) = item;`) declares variables, not element names, and isn't touched.

## Not reported

- **Public API** (unless `stylebro_rename_public_api = true`): Tuple element names in the types of a member's signature (return, parameter, property, field or event types) that other assemblies see, that is public, protected or protected internal in types that are visible too. Renaming them breaks code outside the solution. Internal code is renamed, also with `InternalsVisibleTo`.
- **`_`** and names that don't start with a letter.
- **Names a member has to take from a library member it overrides or implements**, like StyleCop: the library can't be
  renamed. An override or implementation of a member in the solution is reported, and renamed together with it.
- **Names in tuple literals and names a literal infers** (`(count, name)` with variables of those names). StyleCop
  checks inferred names only with `includeInferredTupleElementNames`, off by default; StyleBro doesn't check them.
- **A new name that would be a keyword** (`Var` in camelCase).

## Reported but not fixed

A rename that would add compile errors (or CS8123 warnings) anywhere in the solution is skipped, and the warning stays:
for example a tuple that already has the new name (`(int count, int Count)`), or an override of a library member whose
own signature names the elements.

## Compared with StyleCop

Same reports as StyleCop 1.2.0-beta.556 (checked with the parity set `tuple-element-casing`). StyleCop's `master`
(unreleased, d1b6183d) no longer reports names in the signature of an override or interface implementation; StyleBro
still does and renames them together with the base (master's fix renames only the base, which then fails with
CS8139 on the override). StyleCop's fix renames only the declaration, so every use (`item.count`) and every override breaks the
build; StyleBro renames them together.
